# Native Office integration and patch retirement

Updated November 17, 2026 on `feat/office-semoss-ui`.

The file views retain the upstream Word, Excel, PowerPoint and Visio shells. SEMOSS owns access checks, loading, Save, refresh and downloads. Each format remains lazy loaded. The previous private custom toolbar/canvas surfaces have been removed from this branch; their implementation remains in its Git history at `de540c85d`.

PowerPoint's peer requirements also require i18next 26, react-i18next 17 and lucide-react 1 in the owning packages. The lockfile is generated by pnpm 10.13.1. Builds in a new worktree need the local SDK, UI and renderer artifacts first.

Each full viewer receives a stable customization object. `capabilities.share: false` removes sharing UI. Word/Excel retain their granular `hiddenActions` filters; application workflows such as local Open, Export, Print and Options are suppressed with capabilities. PowerPoint retains its supported ribbon/dialog/panel restrictions and hides the duplicate Quick Access toolbar: SEMOSS Save and the captured Ctrl/Cmd+S own persistence. Copy and normal document editing remain available subject to permissions and document protection.

The SEMOSS color/font/density token bridge was removed. Word/Excel use their public theme props; PowerPoint uses the upstream light/dark theme catalog; Visio inherits the scoped Office theme. The host frame and errors still use SEMOSS components. The existing PowerPoint CSS scoping plugin is retained to keep vendor utility classes out of surrounding host UI.

That shared Vite plugin also explicitly prebundles the nested `@xmldom/xmldom` and `jszip` dependencies for Visio's development workers. Without it, Vite serves CommonJS directly and the parser worker fails because `DOMParser` is not a browser ESM export. All four hosts already install the plugin. This is host build configuration, not another dependency patch.

## Save contracts

- Word/Excel retain their source-aware `useOfficeEditorSession` and `useOfficeFileCommands` integration, including validating the active spreadsheet cell before serialization and acknowledging only a successful unchanged revision.
- PowerPoint obtains `getSaveSnapshot()`, persists its content through SEMOSS and calls `acknowledgeSave(revision)` only after a successful write for the same source. Newer edits stay dirty. A false write result, lost permission, rename/source replacement or failed write never clears dirty state.
- Visio awaits `controller.commitTextEdit()` and permits export only for `committed` or `unchanged` outcomes. It preserves source/rename and generation guards around export and persistence. Refused/cancelled commits abort Save. The recovery hook consumes the new outcome statuses and keeps refused drafts copyable.

## Patch disposition

| Old patch behavior | Disposition |
| --- | --- |
| pptx-react-viewer 4.45.0 native Save interception and premature-success suppression | Entire patch removed. Use public snapshot/acknowledgement API; duplicate native Save chrome is hidden and host shortcuts are captured. |
| ooxml-ui 1.21.0 Visio Save event interception | Removed; upstream now supports cancelable file commands. |
| ooxml-ui 1.21.0 boolean element text-commit API | Removed; use upstream typed controller commit API from #287. |
| ooxml-ui Visio formatted-text fallback | Retained in a new 1.54.1 patch; current native inline editing still chooses a rejected plain-text transaction for some formatted/stencil labels. |
| ooxml-ui Visio draft-outcome notification | Retained in the 1.54.1 patch, using upstream outcome statuses. The full native viewer still does not forward automatic commit results to a host callback/event. |
| Visio `capabilities.share: false` leaves the new ribbon Share button visible | Newly verified upstream defect, fixed in the retained 1.54.1 UI patch. The Share action now observes capability changes and refuses opening while disabled. |
| ooxml-core Visio connector/master formula handling | Retained and ported to 1.53.1 in the six shipped Visio/UI/automation ESM/CJS bundles. The unpatched release still rejects the sample. |

The 1.54.1 UI patch is limited to the Visio bundle. It retries only `replace-plain-text` failures carrying `UNSUPPORTED_TEXT_EDIT`, through the existing validated range-edit operation. Other failures remain refusals. Its event forwards outcomes without changing them. It also synchronizes the ribbon Share action with the public capability. The core patch recognizes narrow self-trigger/master-local formula cases; it does not turn off dependency validation.

## Upstream ticket drafts

These are proposed issue bodies, not posted issues. Include a minimal sanitized fixture rather than an unreviewed private document. Recheck existing issues before filing.

### 1. VSDX: recognize connector self-triggers and master-local text formulas during dependency validation

**Observed on:** ooxml-core 1.53.1.

**Reproduction:** Open a drawing containing a top-level connector whose `BegTrigger`/`EndTrigger` is `_XFTRIGGER(EventXFMod)` (or its explicit same-sheet spelling), plus independent page labels. Execute a supported `replace-text-ranges` label edit. The sample fails with `EDIT_UNKNOWN_DEPENDENCY`: `BegTrigger on shape 26 has dynamic ShapeSheet dependencies that cannot be followed.` After handling that trigger, independent master-local text-size and `XCon` formulas also need correct scope.

**Expected:** Recognize the exact self-event trigger and scope a master's local text reads to that master. Permit unrelated label edits without changing formulas, cached unrelated values, other shapes or package parts.

**Acceptance:** Cover unqualified/qualified self-triggers; independent master text-size and `IF(OR(STRSAME(SHAPETEXT(TheText),""),HideText),5,0)` cases; reject cross-shape triggers, invalid/deleted shapes, malformed or genuinely unknown dependencies. Exercise both range edits and formatting, ESM/CJS, UI and automation entry points. Our negative test still refuses `_XFTRIGGER(Sheet.999!EventXFMod)`.

**Local workaround:** `patches/ooxml-core@1.53.1.patch`. Retire once equivalent upstream behavior passes these fixtures.

### 2. VSDX: use validated range editing for formatted single-run and stencil inline text

**Observed on:** ooxml-ui 1.54.1, after the dependency-scope issue above is addressed.

**Reproduction:** Edit an inline label parsed as one run but containing native formatting markers, or a stencil instance with its own formatted text. Native inline editing selects `replace-plain-text`, which refuses with `UNSUPPORTED_TEXT_EDIT` even though `visioTextDraftEdit(..., { ranges: true })` succeeds on the same target and preserves the package.

**Expected:** Choose the appropriate supported range transaction, or narrowly retry it after this specific plain-text refusal. Do not retry protection, stale/cancelled operations, unknown dependency or other transaction failures.

**Acceptance:** Edit, undo/redo, export and reopen affected labels, preserving formatting and all unrelated parts. Include single-run markers, stencil overrides, ordinary plain text and genuinely unsupported fields. Cover the full viewer and standalone canvas.

**Local workaround:** the range-fallback hunk in `patches/ooxml-ui@1.54.1.patch`.

### 3. VSDX: forward typed text outcomes from every native full-viewer commit path

**Related:** [#287](https://github.com/ChristopherVR/ooxml/issues/287) added an awaited commit result; this request concerns automatic commits whose caller is the native UI.

**Reproduction:** In the full `VisioViewer`, type a draft the edit engine refuses, then blur or change tools. The native editor closes and the automatic commit resolves internally. A later host `controller.commitTextEdit()` may report `unchanged/no-draft`, and the full-viewer binding exposes no typed text-outcome callback. The host cannot recover the refused text from that result.

**Expected:** Emit or forward `TextEditOutcome` for all completion paths, including automatic blur/Escape/tool/page changes and permission changes, through a documented native element event and framework callback. Return the same outcome from explicit commits; preserve draft text with source/document generation and shape/page identity.

**Acceptance:** Host recovery retains rejected/cancelled drafts even if automatic commit finished before Save; committed corrections remove the matching failure; stale outcomes never apply to a different source; multiple viewers remain isolated; unmount is safe. No private canvas access or commit interception should be required.

**Local workaround:** the outcome-notification hunk in `patches/ooxml-ui@1.54.1.patch`. Remove only after adapting the recovery hook to the upstream event/callback.

### 4. VSDX: honor `customization.capabilities.share: false` in the native ribbon actions

**Observed on:** ooxml-ui 1.54.1 and visio-react-viewer 1.4.1, using the full native viewer.

**Reproduction:** Mount `<VisioViewer customization={{ capabilities: { share: false } }} collaboration={null} />` and load a drawing. The native ribbon still renders its Share button. `attachVisioShare` unconditionally creates the shared ribbon actions and never synchronizes their `noShare` property with the viewer's customization. The action's dialog opener also lacks the capability guard.

**Expected:** The documented Share capability removes that button and prevents its UI action opening the Share dialog. Setting the capability back to true/omitting it restores the default UI for that instance.

**Acceptance:** Check initial mount, live false/true/null customization updates, narrow layout, File/search entry points and multiple viewers. Disabled sharing must remain absent after locale changes. Keep direct host collaboration APIs and document permissions conceptually separate from hiding UI.

**Local workaround:** the Share synchronization/guard hunks in `patches/ooxml-ui@1.54.1.patch`. Word, Excel and PowerPoint honor their configured sharing suppression in browser checks; this ticket is specific to Visio's native ribbon.
