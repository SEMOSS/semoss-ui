# Internationalization

`@semoss/i18n` is the one place locale JSON lives for every SEMOSS app. It wraps i18next and
react-i18next and adds a small lazy backend, so an app ships only the language in use.
Package rules and commands are in [libs/i18n/AGENTS.md](../../libs/i18n/AGENTS.md). The
procedure for changing keys is [skills/add-translations.skill.md](../../skills/add-translations.skill.md).

## Two Tiers of Translations

- **Core** namespaces are used by every app: `common` (buttons, labels, actions),
  `validation` (form validation messages) and `notifications` (notification templates).
  They sit at `locales/<lang>/*.json`.
- **Package-specific** namespaces sit in a folder per owner under `locales/<lang>/`, plus
  `shared/` for namespaces that more than one app reads.

Languages are listed in `LANGUAGES` in `src/constants.ts`; `en` is the default and fallback. The
builder sets `<html lang dir>` whenever the language changes, so right-to-left languages flip.

## Lazy Loading

Locale JSON is never statically imported into an app's main chunk.

- Each app passes one `LazyResources` map to `new I18nBuilder(resources, options)`.
- `builder.ts` registers a tiny i18next **backend**. Its `read(language, namespace)` calls the
  map's loader for that namespace. i18next calls it at init for the active language, and
  again on `i18n.changeLanguage()`.
- i18next loads base languages only (`load: "languageOnly"`), so `en-US` resolves to `en`.
- A namespace with no loader, or any loader that rejects (including a missing file or failed
  chunk), resolves to an empty bundle. i18next then silently falls back per key to English.
  Check the browser network and console when diagnosing missing translations.
- Apps `await i18nBuilder.ready` in `main.tsx` before the first render, so the first paint has
  real strings instead of raw keys.
- Namespaces not in `ns` are fetched on demand. Lazily loaded code calls
  `preloadNamespaces([...])` as it mounts (the client's embedded terminal does this), and
  react-i18next re-renders on the `loaded` event.
- The client passes `lockToEnglish: true`, which pins `lng: "en"` and skips language
  detection. Every other app detects from `localStorage` (`smss-language`), then the browser.

Lazy loading does not fix the initial bundle size or request count. Consumer apps own the
locale chunk grouping in their `vite.config.ts`, so verify the affected app's build output and
network requests when changing how languages or namespaces load.

## Package-Specific Resources

| Loader map | File | Used by |
|---|---|---|
| `clientResources` | `resources/client.ts` | `@semoss/client`, `@semoss/automation` |
| `playgroundResources` | `resources/playground.ts` | `@semoss/playground`, `@semoss/collaboration` |
| `terminalResources` | `resources/terminal.ts` | `@semoss/terminal` |
| `auditlogResources` | `resources/auditlog.ts` | `@semoss/auditlog-package` |

Every map includes the core namespaces. A shared namespace appears in each map whose app reads
it.

## Translation Namespaces

A namespace is one JSON file. Keys are addressed as `namespace:path`, such as
`t('common:buttons.save')`. The namespace name is the key in the loader map, not the file path. `chat-tools.json`, for
example, is registered as `chatTools`.

## Resource Export Pattern

Each loader map is a `LazyResources` object (see
[playground.ts](../../libs/i18n/src/resources/playground.ts)). Its `ns` namespaces preload at init
for the active language, so above-the-fold text renders without a flash of raw keys; `load` maps
each namespace to a dynamic `import()`.

The template-literal `import()` makes the bundler emit one chunk per language file. Adding a
namespace is one `load` entry, plus an `ns` entry if it must render before user interaction.
A static top-level import would defeat the lazy loading.
