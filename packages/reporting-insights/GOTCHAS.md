# Reporting Insights — Gotchas & Painpoints

Running log of non-obvious traps, SEMOSS quirks, and hard-won lessons for this
package. Read before touching MCP, the portal, dashboard persistence, or doing an
upstream integration.

---

## 1. Two diverged copies of this app

There are **two** reporting-insights trees and they have **diverged**:

- **SRC (upstream git repo):** `…/mde-medical-review-helper/reporting-insights`
  (git root is the parent; tracked paths are prefixed `reporting-insights/…`).
- **DST (the one that ships):** `…/SemossWeb/packages/reporting-insights`
  (lives inside the SemossWeb git repo; our platform work is uncommitted here).

DST has heavy local divergence from SRC (our styling: `DashboardNav` left rail vs
upstream `SheetTabs`, `useHeaderSlot` header, mobile drawer, `@semoss/ui`
components, MCP host, redeploy-on-save, AI-as-its-own-page, embedded mode, etc.).

### Integrating an upstream pull — DO THIS

1. Get the exact commits: `git log --oneline <base>..<head>` in SRC. Read each
   commit message — features are per-commit (e.g. "add facet drop area",
   "layout preservation", "param sync to legacy dashboards").
2. For each changed file, **3-way merge**:
   `git merge-file -p -L ours -L base -L upstream <DST/file> <base-blob> <upstream-blob>`
   where base = the previous upstream commit you last integrated.
   Most files merge with 0–1 conflicts.
3. **`NewDashboardPage.tsx` is special** — it's the most diverged file (DashboardNav
   vs SheetTabs render bodies produce a ~1,300-line unresolvable conflict). Do NOT
   wholesale-overwrite it with upstream (that silently drops our styling AND misses
   features). Instead: **graft each commit's `NewDashboardPage` hunks surgically**
   into our file. The feature LOGIC lives outside the giant render conflict, so it
   grafts cleanly.
4. **Verify completeness per file.** After grafting, extract the upstream-added
   lines (`diff base upstream | grep '^>'`) and grep each substantive/logic line in
   DST. This is how we caught missed features (facet wiring, tabColor picker,
   `useTabColors` in the viewer, layout preservation).

### The trap we hit
"Overwrite NewDashboardPage with upstream, re-apply a few platform edits" **loses
our styling and silently drops features.** Restoring our version + surgical graft is
correct but you must audit EVERY commit's hunks or you'll miss things (we missed
facet drop area, layout preservation, filter-widget persistence, color-tabs picker,
and the viewer's `useTabColors` on the first pass).

## 2. Files exist twice: `src/` (app) vs `portal/` (deployed dashboard)

- `src/pages/DashboardPage.tsx` = the in-app viewer (React app).
- `portal/components/ViewMode.tsx` = the deployed dashboard viewer (standalone
  bundle served from `public_home/<id>/portals/`).
- `portal/components/EditMode.tsx` mirrors `NewDashboardPage` but **is not reachable
  from any UI** (no `setMode('edit')` trigger) — the portal is view-only in practice.

A feature that touches "the dashboard view" usually needs applying in BOTH
`DashboardPage` and `ViewMode`, plus the editor `NewDashboardPage`. Example:
`useTabColors` + the `onRenderTab` tab-color branch had to be added to all three.

`portal/dist/index.html` is a **build artifact** — never hand-merge it; it's
regenerated by `npm run build:portal`.

## 3. SEMOSS MCP tools

- Tools are generated in `src/services/mcpManifest.ts` and shipped as two assets per
  project: `mcp/py_mcp.json` (manifest, `"_type":"python"`) and
  `py/mcp_driver.py` (the functions; function name == tool name).
- **The Python function's returned dict is surfaced to the LLM in full** (via
  `RunMCPToolReactor`) — not just its `url`. So tools can return real DATA
  (search results, rows, structure), not only a link. Data tools omit
  `_meta.SMSS_MCP_UI`; UI tools (open a page inline) set it.
- **`resourceURI` is PORTAL-RELATIVE and must start with `/`.** The playground
  concatenates it: `${MODULE}/public_home/<id>/portals${resourceURI}`. An absolute
  `http(s)://` URL produces `…/portalshttp://…` and 404s. The host project's portal
  is a hash-aware redirect that forwards `/#/route` to the deployed app.
- **Filter params** reach a dashboard portal via the `SMSS_INIT_TOOL` postMessage
  (buffered in `portal/main.tsx` at module scope BEFORE React mounts — the bundle is
  large so a `useEffect` listener registers too late and drops the one-shot message)
  and/or URL query params. See `externalParams` in `ViewMode`.
- **Host re-sync is version-gated.** `WorkspaceProvider` only re-uploads the host
  manifest/driver when `HOST_ARTIFACT_VERSION` (in `mcpManifest.ts`) or the app URL
  changes (cached in `localStorage['ri-mcp-host-sync']`). **BUMP
  `HOST_ARTIFACT_VERSION` whenever you change `buildHostMcp` or the redirect HTML**,
  or clients keep the stale host.
- The Python driver runs server-side and CAN read dashboard.json files off disk and
  run SQL via `from gaas_server_proxy import ServerProxy; sp.callReactor(...)`. The
  exact `callReactor` epoc/result shape is server-specific — wrap it in try/except
  with a graceful fallback (return the SQL) so a tool never hard-errors.
- Driver base-path discovery: the driver walks up from `__file__` (and SEMOSS
  base-folder env vars / cwd) to find the `project/` dir that contains
  `*/app_root/version/assets/portals/dashboard.json`. Don't hardcode absolute paths.

## 4. SEMOSS pixel / SQL quirks

- Run SQL with: `Database(database=["<engineId>"]) | Query("<sql>") | Collect(N);`
  — always via **engine id (UUID)**, not the display name (`Alphabet2` →
  `ba851343-…`).
- **SEMOSS reports bad SQL as an `ERROR` `operationType`, it does NOT throw.** Check
  `pixelReturn[0].operationType?.includes('ERROR')` and read the real message from
  `output`. See `QueryRunner`, `testQuery`, `McpCreatePage.runSql`.
- Result shape varies: read `output.data.headers` / `output.data.values` (fall back
  to `output.headers` / `output.values`).
- **`headerInfo` types are unreliable** (often all-STRING). Infer column types from
  the actual sampled values; only fall back to `headerInfo` when a column has no
  data. (This bit us with everything showing as STRING.)
- Escape SQL for the pixel string (`escapeSqlForPixel`): `"`, `\`, newlines, tabs.
- Identifiers: do **not** wrap table/column names in quotes for generated SQL
  unless a join forces qualification; unnecessary quoting broke queries.

## 5. Parameters / Run All

- The **Parameters sheet** is auto-synthesized (`ensureParamSheet` in
  `resolveQuery.ts`, id `sheet-0`) whenever any query has a param — including for
  legacy dashboards, inline at load/init (NOT via a post-mount effect, which raced
  the tab bar). Run All only appears on that sheet; a param-less dashboard has none.
- In the **editor**, the Parameters sheet was historically a dead preview
  (`allSatisfied={false}`, `onRunAll={()=>{}}`). It now runs all queries with the
  entered values via `runAllQueries` — mirror any change in `DashboardPage` /
  `ViewMode` viewers, which have their own `handleRunAll`.
- `isParamSatisfied` treats multiselect as always-satisfied (empty = all).

## 6. FlexLayout tab coloring

- Tab colors are injected as a global `<style>` by `useTabColors` (`lib/tabColors.ts`)
  keyed off `[data-tab-id]`, which `onRenderTab` wraps the tab content with.
- **Color the WHOLE tab and force text color on children.** Original bug: the
  selected rule set the bg to white with a 2px top accent + light text → "only the
  top is colored, unreadable font." Fix: fill both idle+selected with the color
  (selected = a darker shade), `box-shadow:none`, and set `color`/`fill` with
  `!important` on the button AND `*` (FlexLayout renders the label in children).

## 7. Config drop zones

- `VizConfigTabs` → `VizConfigDropZones` render the X/Y/Tooltip/Facet zones. The
  aggregation control is `@/components/ui/SearchableSelect`, whose trigger is
  `w-full` — in a single flex row it **squeezes the column name to zero width**. Fix
  was a **two-line chip** (name row + aggregation row). Same class of bug hit the
  "In table" items earlier.

## 8. Embedded / read-only preview

- `lib/embed.ts` `isEmbedded()` = in an iframe (playground) or `?embed=1`. When true,
  `MainLayout` hides `AppHeader` and `DashboardPage` hides its management toolbar
  (Edit/Share/Delete/back) → a clean read-only render for the tool preview.

## 9. Build / verify

- Build: `pnpm exec turbo run build --filter=@semoss/reporting-insights` from the
  SemossWeb root. `noUnusedLocals` is ON — dead imports fail the build (common after
  removing a feature like the master-viz concept; delete the now-unused imports).
- Syntax-check any generated Python driver before shipping: extract the
  `String.raw` block and `python3 -m py_compile`. You can also unit-test the pure
  file-I/O tools against the real `…/Semoss/project/*/…/dashboard.json` files.
- **Constraint for this effort:** do NOT commit or push — keep everything
  uncommitted; build-verify after each change.

## 10. Cross-source data products (multi-frame joins)

- A `DashboardQuery` with `sources` (≥2 legs) + `joins` is a **data product**: each leg
  is materialized into a GRID frame and merged. All pixel construction goes through
  ONE builder — `src/lib/queryPixel.ts` `buildQueryPixel()` — shared by the editor,
  app viewer, portal, AND (as a Python mirror) the MCP driver. Change the pixel shape
  in ONE place.
- **Merge syntax — the one that actually works.** Import each leg into a GRID frame, then
  merge as a **separate statement per join with an explicit `QueryAll()`**, and Collect the
  base at the end:
  ```
  Database(["dbA"]) | Query("<encode>…</encode>") | Import(frame=[CreateFrame(frameType=[GRID], override=[true]).as(["S1"])]);   // base
  Database(["dbB"]) | Query("<encode>…</encode>") | Import(frame=[CreateFrame(frameType=[GRID], override=[true]).as(["S2"])]);   // incoming
  Frame(frame=[S2]) | QueryAll() | Merge(joins=[(baseCol, inner.join, incomingCol)], frame=[S1]);   // pipe incoming, arg = base
  Frame(frame=[S1]) | QueryAll() | Collect(20);                                                       // collect the base
  ```
  Two non-obvious rules from `MergeReactor.java`, both learned the hard way:
  1. **`getFrame()` returns the `frame=[…]` ARGUMENT (not the piped frame), and the merged
     result is stored back under that argument's name.** So to accumulate the merge in the base
     (and collect it), you **pipe the INCOMING leg and pass the BASE as `frame=[…]`**. Piping the
     base and passing the incoming as `frame=[…]` silently lands the result in the incoming frame,
     so `Collect(base)` returns UN-merged data.
  2. The generated SQL is `FROM <frame=arg=base> AS A <type> JOIN <piped=incoming> AS B ON (A.<t0> = B.<t2>)`,
     so the tuple is **`(baseCol, joinType, incomingCol)`** — `A` = base, `B` = incoming.
  Column names are **bare** (the reactor resolves same-named columns by alias). Chaining
  `… | Merge(…) | Collect(N)` in one statement without `QueryAll()` errors. Cross-DB requires
  both legs materialized as GRID frames first (a raw cross-DB SQL JOIN throws
  "Joining tables across databases is not possible").
- **Orientation & outer direction are auto-derived, not assumed.** The user can assign either
  column to left/right; `buildQueryPixel`/`_dp_pixel` figure out which side is already in the
  base vs. which leg is being merged in (`merged` set), pair each column with its owning leg,
  and map the outer direction so "keep leftAlias/rightAlias's rows" is preserved (A=base → keep =
  `left.outer.join`; B=incoming → keep = `right.outer.join`; inner is symmetric).
- **Read the LAST `pixelReturn`, not `[0]`.** A data product emits N `Import` + M `Merge`
  statements then the `Collect`. Use `lastPixelOutput(pixelReturn)`; single-source has one
  entry so it's identical. The `runPixel` callback (NewDashboardPage VizCard) was changed
  to return the last output for the same reason.
- **Reserved-word columns break the merge.** SEMOSS's merge builds a
  `CREATE TABLE … AS SELECT B.<col> …` and does NOT quote identifiers, so a frame column
  literally named `Group`/`Order`/… (or with spaces/symbols) makes H2 throw
  `expected "identifier"`. It only errors when that column is on the joined-in (B) side,
  hence "works one direction, not the other." Fix: `aliasReservedColumns()` in
  `queryPixel.ts` wraps each leg's SQL (`SELECT "Group" AS "Group_c", … FROM (<sql>) __ri_sub`)
  and the DataProductModal remaps join columns to the safe names — baked into the SAVED leg
  SQL (so app/portal/MCP all stay safe). It auto-fetches a 1-row sample to learn columns.
- **Shared column names across legs corrupt the merge — the subtle one.** If two legs
  output a column with the *same* name (e.g. both tables have `LETTER`, `NUMBER`, `PHRASE`),
  SEMOSS does NOT keep `S1.LETTER` + `S2.LETTER` after the merge — it folds the incoming
  side into the base's same-named column. Symptoms: an INNER join returns *all base rows*
  (because the incoming leg contributes no new columns, so the join degenerates instead of
  filtering), and LEFT/RIGHT joins `null` out exactly the shared columns. Worst of all it
  errors nothing — you just get silently wrong data. Fix: `resolveLegColumns()` in
  `queryPixel.ts` detects any column name present in >1 leg and prefixes it with the leg
  alias (`LETTER` → `s1_LETTER` / `s2_LETTER`) in that leg's wrapping SELECT, then remaps
  the join specs — baked into the SAVED leg SQL. Columns unique to one leg keep their name.
  (This subsumes the reserved-word aliasing: a prefixed/sanitized name is also identifier-safe.)
- **Test joins with matching key types AND real overlap.** A join on `SEASON` (Spring/…)
  = `PHRASE` (apple/…) has zero logical matches, so even a correct inner join returns 0
  rows. And a numeric key vs a string key triggers engine-level `CAST(... AS DOUBLE)` which
  fails on non-numeric text. Join same-typed keys that actually overlap (e.g. `LETTER`=`LETTER`).
- **Merged column names** are decided by SEMOSS's Merge (collisions may be renamed). The
  DataProductModal's "Preview result" shows the ACTUAL joined headers — bind the chart to
  those, don't guess.
- **Join types**: `inner` → `inner.join`, `left` → `left.outer.join`, `right` →
  `right.outer.join`. Only inner/left were seen validated in MergeReactor's filter logic;
  if `right` misbehaves live, emit it as a left-outer with operands swapped.
- **Cross-engine merge requires materialized frames** (we always `Import` into GRID first);
  a raw cross-DB SQL JOIN errors "Joining tables across databases is not possible."
- Data products **skip table pagination** (the DB task iterator can't page a merged frame)
  — they always `Collect(-1)`.
- Frame names are `RI_<saltHash>_<ALIAS>` with `override=[true]`; the salt defaults to a
  hash of the legs so concurrent distinct products don't clash.
- The single-source `databaseId`/`query` fields are kept (pointed at leg 0 + a
  `-- Data product: …` description) but ignored while `sources.length >= 2`. Removing the
  product (the ✕ next to the toolbar badge) clears `sources`/`joins`.

## 11. zsh footguns (when scripting these tasks)

- zsh does **not** word-split unquoted vars — a multi-file `for f in $FILES` where
  `FILES` has newlines iterates once over the whole blob. Use a zsh array
  `files=( … )` or `printf '%s\n' … | while read -r f`.
- `git show <sha>:path` needs the **repo-relative** path (here prefixed
  `reporting-insights/…`); the `-- path` filter form silently returned empty for us.
