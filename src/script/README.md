# Generate @semoss/sdk from backend contracts

This generator emits TypeScript for `@semoss/sdk`. The initial selection contains
`HealthResource.readiness` and `StopPixelExecutionReactor`. It replaces the previous
manually maintained REST/reactor catalogs; it does not migrate the backend catalog.

## Run

Use Node 24, the repository's pnpm install, Maven, and JDK 21. Compile SEMOSS and
Monolith against the matching SEMOSS artifact first. The backends need
`target/classes` and their dependencies in the local Maven repository. If Maven
reports a missing offline dependency, resolve it through the backend's normal build.

From the semoss-ui root:

```sh
pnpm --filter @semoss/sdk generate --semoss /path/to/Semoss --monolith /path/to/Monolith
pnpm --filter @semoss/sdk generate:check --semoss /path/to/Semoss --monolith /path/to/Monolith
```

`SEMOSS_DIR` and `MONOLITH_DIR` also work. When omitted, paths are discovered from
sibling checkouts named `Semoss` and `Monolith` under the UI checkout's ancestors.
`JAVA_HOME`, when set, selects both `javac` and `java`.

For normal frontend development or CI without backend checkouts:

```sh
pnpm --filter @semoss/sdk generate --from-contracts
pnpm --filter @semoss/sdk generate:check --from-contracts
pnpm --filter @semoss/sdk test:generator
pnpm exec tsc -p src/script/tsconfig.json
```

`--from-contracts` replays the committed JSON snapshot. Only a live run checks
agreement with the current backend sources. `--check` compares all generated bytes
and the owned-file manifest, exits nonzero on drift, and does not write SDK files.
Live reads use a temporary compilation directory and refresh the backends' Maven
classpath files under `target/`.

## Last successful sync

Every successful live `generate` also writes [semoss-sync.json](../../semoss-sync.json)
at the UI root. `lastSyncedAt` records the UTC completion time; `contractsSha256`
identifies the canonical contract snapshot that was synced. The target is
`@semoss/sdk`. Check this record in alongside the generated output.

The record updates after all generated files have been saved, including when the
backend read succeeds with no output changes. Failed runs preserve the previous
record. `--check` and `--from-contracts` leave it unchanged because they do not
perform a new backend-to-SDK sync. The timestamp lives outside the contract graph
and TypeScript files so their bytes remain deterministic.

## Data flow and ownership

1. [sdk-operations.json](./sdk-operations.json) selects Java classes and methods.
   It contains no hand-maintained descriptions, payload types, or requiredness.
2. [ExportContracts.java](./sdk-generator/ExportContracts.java) uses the shared
   `prerna.contract.ContractReader`. The command freshly compiles the contract
   package, `AbstractReactor2`, and the selected application/resource/reactor
   sources into a temporary directory. Backend `target/classes` and Maven jars
   supply dependencies. Rebuild the backends when changing those dependencies or
   unselected supertypes. The exporter uses `Class.forName(..., false, ...)` and
   never constructs resources/reactors or calls their operations.
3. [operations.json](../../libs/sdk/contracts/operations.json) stores the versioned
   contract graph: descriptions, policies, deprecations, binding details, HTTP
   statuses, invocation semantics, diagnostics, and opaque type references.
   Shape discriminators preserve integers versus decimals, optional versus
   nullable properties, enums, collections, maps, unions, and recursion.
4. [render-sdk.ts](./sdk-generator/render-sdk.ts) maps that graph to TypeScript.
   It emits [health.ts](../../libs/sdk/src/api/health/health.ts), the private
   [reactor catalog](../../libs/sdk/src/lib/reactors/catalog.ts), and its runtime
   [inventory](../../libs/sdk/src/lib/reactors/inventory.ts). Existing transport,
   `useAPI`, `buildPixel`, `runPixel`, and hooks consume those outputs.

Contract and TypeScript output has stable ordering, no timestamps or machine-specific paths, and uses
the pinned repository formatter. Check in the JSON and generated TypeScript
together. Do not hand-edit generated files. A manifest tracks owned files so an
ignored operation disappears from the SDK. A fully ignored REST group keeps an
empty module for its curated package entry. Removing a group from the selection
also requires removing its package export/build entry; the generator then removes
its previous output. Deletion is limited to generated paths carrying the header.

REST application prefixes come from `@ApplicationPath`; JAX-RS supplies method,
resource path, media types, and bindings. This initial exporter assumes the
deployment's servlet mapping agrees with `@ApplicationPath` (as HealthApplication's
`/health/*` mapping does). It does not discover servlet overrides or subresources.
Pixel names follow the ordinary `ReactorFactory.loadFromCP` convention: remove the
`Reactor` suffix. Frame-specific variants, aliases registered in factory maps, and
plugin registries require a backend registration contract before selection here.

## Supported contracts and policies

- The current REST adapter supports JSON `GET` endpoints, required scalar path
  parameters, and scalar/repeated scalar query parameters. Other verbs, request
  bodies, headers/cookies/matrix bindings, nullable query values, alternate media
  types, and ambiguous bindings fail explicitly. Add and test an adapter before
  selecting such an endpoint. The package currently publishes the `health` group;
  adding another group also requires its curated package export/build entry.
- Pixel inputs support named aliases, declared positional order, trailing optional
  positions, and a final variadic input. Optional inputs do not make the whole
  argument optional: only `canOmitParameters` does that. Runtime serialization
  retains the existing literal/`rawPixel` behavior; TypeScript contracts do not
  validate JavaScript callers or backend responses at runtime.
- `@Ignore` excludes a selected operation. `@Internal` adds a caution while keeping
  it available. Java `@Deprecated` plus supplemental metadata generates deprecation
  documentation. These are independent policies and never change authorization.
- Reader diagnostics, unknown requiredness, missing references, unverified types,
  name collisions, and unsupported adapters fail generation. Explicit `@Dynamic`
  payloads can map to `unknown` with their reason retained in the contract.
- TypeScript uses `number` for both integers and decimals. The JSON retains that
  distinction; numeric precision and wire-format validation remain caller concerns.

The readiness annotations describe both bodies as an enum status and a boolean.
The generator does not invent a status-to-literal correlation: `ready()` returns
`ReadyResponses[200]`, and `ReadyResponses[503]` describes the error body. The
existing transport throws `ApiError` for 503, with unvalidated `data: unknown`.

## Add an operation

Annotate it in the backend and describe structured output using inline fields or
contract records. Add the class/method to the selection, compile its backend
dependencies, regenerate, review diagnostics and the diff, and run the checks
above plus the SDK tests and build integration suite. No operation is included
merely because it exists; the selection bounds this initial example rollout.
No `@Ignore` marker is needed for every other backend operation.

The backend development guide is
`Semoss/docs/development_guides/operation_contracts.md`. SDK usage examples are in
the [SDK README](../../libs/sdk/README.md#generated-api-and-pixel-examples).
